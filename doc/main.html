1. はじめに

1-1. 本書の内容

本書では、Aliexpressなどで格安で販売されている中古品FPGAボード EBAZ4205 を用いて、FPGAのロジック回路を用いたEthernet通信処理の方法について説明します。

ボード上に搭載されているEthernet PHYとの通信方法から、最終的にはいわゆる ping コマンドに応答できるように、 ICMP Echo Requestに対する処理まで実装します。 TCPなどセッション管理や順序制御、再送といった複雑な処理を必要とするトランスポートは扱えませんが、本書の延長線上でUDPを扱うことが可能です。

本書の対象とする読者は、「FPGAを触ったことがあるがEthernetを直接扱ったことはないので試してみたい」という方です。

よって、本書では、FPGAの論理回路の記述に SystemVerilog を用います。ただし、SystemVerilog の文法などについては特に説明しません。 また、FPGAの論理合成や配置配線作業の細かい点についても説明しません。そのあたりは、それぞれ専門の書籍を参照してください。

2. EBAZ4205について

EBAZ4205はマイニング用演算回路の制御に用いられている基板です。 制御回路の主要素子として、Xilinx の Zynq-7000 シリーズのFPGAが用いられています。 マイニング用演算回路の制御ボードなので、本来単品では出回らないはずなのですが、どうもマイニング用装置が型落ちとなって廃棄されているのか、分解した部品が中古品として Aliexpress などで $15~$25程度で販売されているようです。

搭載されているFPGAは XC7Z10-CLG400 という型式で、Zynq-7000シリーズの中では最も小規模なものです。 それでも、FPGA部分のロジック数は 23K、DSPスライス 80個に加えて、Arm Cortex-A9のコアを2つ搭載しています。

このようなデバイスなので、デバイス単品の価格もそれなりに高く、きちんとした評価ボードは1万円以上します。 中古品かつきちんとした資料が存在しないボードとしても、$15~$25で購入できるEBAZ4205がかなり安いということがわかります。

2-2-2. JTAGアダプタ

SDカードを使う場合、FPGA側への論理回路の書き込み (コンフィグレーション) はSDカード上のイメージから行えるため必須ではありませんが、デバッグなどにはJTAGアダプタが合ったほうが便利です。

EBAZ4205にはXilinx用のピン配列のJTAGコネクタがありますので、Xilinx純正のJTAGアダプタ (Platform Cable USB II等)やDigilentのJTAG-HS3をお持ちの場合はそのまま接続できます。

4. Ethernet MACの作成

4-1. Ethernet通信ハードウェアの構成

EBAZ4205には、100BASE-TXのEthernet接続用ハードウェアがあります。

Ethernet通信を行うハードウェアは、主に物理的な電気信号を扱う PHY と MAC に分かれています。 EBAZ4205の場合は、PHYはFPGAの外にある IP101GA が担っています。 通常の構成では、PHYとFPGAのPS内蔵のMACを接続して、PS上のLinuxからEthernetを使います。

一般的にMACを含むPS側の機能は専用のピンが用意されており、そのピンに対応するハードウェアを接続します。 ただし、対応するピンに配線するのが難しい場合などに、PL側を経由して任意のピンから信号を出力する機能 (EMIO) があります。 EBAZ4205でも、EMIOを使ってPHYとMACの信号が接続されています。

上記のとおり、EMIOはPL側を経由して信号が接続されているので、PL上のユーザーロジックに接続することができます。 ということは、PSのMACに接続する代わりに、PL上にMACを作ればPLからEthernet通信を行えます。

PL側に実装可能なMACとしては、Xilinx公式のEthernet MAC IP (Tri-Mode Ethernet MAC https://japan.xilinx.com/products/intellectual-property/temac.html)があります。 ただし、このIPは有償ですので、遊びで使うのは難しいです。

よって、簡単なEthernet MAC IPを作成します。

4-2. PHYとMACの通信

Ethernet PHYとMACの間の通信は MII (Media Independent Interface) として規格化されています。

MIIは、送受信各方向4bitのデータ線と、データの有効を表す信号、クロック、およびその他の制御信号からなります。 これらのうち、データ線 (RXD, TXD) とデータの有効を表す信号 (DV, EN) とそのクロック (RX_CLK, TX_CLK) を処理すれば通信ができます。

MIIのデータは対応するクロックの立ち上がりエッジに同期して、データ有効信号が 1 の間データが有効として扱われます。 データ線の0ビット目が、物理信号上で時間的に先に送られるビット (つまりLSBファースト) です。

MIIのデータ線は4bitしか無いので、2サイクル分のデータをつなげて1オクテットを復元します。 このとき、あるサイクルの4bitデータが下位4bitなのか上位4bitなのかを決定する必要があります。 そのためには、SFD (Start Frame Delimiter) を検出します。

Ethernetのフレームは (@fig:ethernet-frame) の構造をしています。このとき、数オクテットのプリアンブル (Preamble) につづいてSFDがあります。 SFDは上位4bitと下位4bitで異なる値ですので、SFDの下位4bit→上位4bitのシーケンスを検出することにより、オクテットの区切りとフレームの開始を検出できます。

10. Wio Terminalのハードウェア

10-1. ハードウェア構成

Wio Terminalのハードウェアのブロック図を図2に示します。

以下に、主要なハードウェアの説明を記述します。

10-1-1. ATSAMD51P19A

中央のMCUはMicrochip社の ATSAMD51P19A です。

CPUコアとして最大 120[MHz] 動作の Cortex-M4F コアを1つ持っています。 (ちなみに、SeeedのWio Terminalの説明文には Boost up to 200[MHz] と書かれていますが、データシートを見る限り定格外です。一応筆者の固体では、LCDの描画処理プログラムをCPUクロック200[MHz]で1日間は動かし続けられましたが。) また、内蔵メモリとしてフラッシュ 512[kiB], RAM 192[kiB] があります。

Wio Terminalの他のハードウェアはほとんどATSAMD51P19Aに接続されています。

10-1-2. RTL8720DN

Realtek社のAmeba Dシリーズの無線機能付きSoCです。

CPUコアは Cortex-M0@20[MHz] と Cortex-M4F@200[MHz] のデュアルコア構成です。 また、コアごとに 64[kiB] と 512[kiB] のRAMがあります。

回路図上には記載がありませんが、実際には RTL8720DN を含むモジュールが実装されており、モジュール内にRTL8720DN用のプログラムを格納するSPI Flashが含まれていると思われます。 残念ながらSPI Flashのサイズについても記載がないので不明ですが、おそらく数MBくらいではないかと思われます。

メインMCUである ATSAMD51P19A とは SPI および UART で接続されています。 UART は RTL8720DNのファームウェアの更新、 SPI は無線通信のコマンドのやりとりに用いられます。

また、デバッグ・コネクタ側にも UART の信号が接続されており、こちらからもファームウェアの更新を行うことができます。

CPUコアとSRAMの性能だけみれば、メインMCUの ATSAMD51P19A よりも高性能なので、RTL8720DN側でいかに暗号化通信などの重たい処理を行うかが、Wio Terminalで通信を含む処理をつくるときの鍵となります。

10-1-3. ILI9341

中国 Ilitek社のLCDコントローラICです。 M5Stackで使われている ILI9342C とほぼ同じです。

320x240ピクセルのフレームバッファを内蔵しており、SPI経由で受け取ったコマンドに応じて、フレームバッファ内のピクセルデータを更新することができます。

10-1-4. W25Q32JVZPIM

Winbond社のQSPIフラッシュ・メモリです。ATSAMD51P19Aの内蔵フラッシュとあわせて、プログラムやデータを格納するのに使えます。

使い方については 13-4節で説明します。

10-2. Wio Terminalの分解

Wio Terminalの分解は比較的簡単です。

本体を裏返すと四隅に黒い足があります。 このうち左上と右下の足を剥がした裏側にネジがありますので、足を剥がしてネジを外します。

また、ネジがない左下と右上の裏蓋と本体の間に、本体と裏蓋を固定するための爪がありますので、おらないように本体を外に引っ張りながら外します。

本体側の筐体と基板の間は、液晶と筐体の間の両面テープで接着されていますので、傷つけないように気をつけながら剥がします。

10-3. デバッグ信号の引き出し

Wio Terminalの基板上には、向上出荷時のファームウェアの書き込みのために、ATSAMD51のデバッグ信号、及びRTL8720DNのファームウェア書き込み用UARTの信号が接続されたパッドが出ています。(図3)

このパッドは2.0[mm]ピッチで並んでいるため、2.0mmピッチのコネクタをはんだ付けすれば、デバッグ信号を引き出すコネクタを追加できます。(図4)

ただし、現在の最新リビジョン(rev. 1.2)のWio Terminalでは、Raspberry Piコネクタの上側に、デバッグ信号パッドと同じ信号が接続されたFFCコネクタが追加されていますので、このようなはんだ付けを行わずにデバッグ信号を引き出すことができます。(図5)

FFCコネクタは 0.5[mm]ピッチ, 10ピン のFFC用ですので、対応するケーブルを用意します。

FFCとデバッガの接続には、FFCを2.54[mm]のピンヘッダーに変換する基板を使います。 FFChttps://www.aitendo.com/product/7614と変換基板https://www.aitendo.com/product/18491のどちらも、aitendoやAmazonで購入できます。

10-4. ATSAMD51のクロック構成

10-4-1. クロックシステム

ATSAMD51のクロック・システムはそこそこ複雑で、ある程度理解していないとペリフェラルを触るときに困るので、クロック構成について説明します。 ATSAMD51のクロック周りのブロック図を図6に示します。

ATSAMD51のクロックは、 GCLK (Generic Clock Controller) により分配されます。 GCLKは GCLK0~GCLK11 の12チャネルのクロック･ジェネレータから成ります。 各チャネルにはクロック源を選択するマルチプレクサと、マルチプレクサで選択したクロックを分周する分周器があります。

GCLKのクロック源としては、OSCULP32K, XOSC32K, XOSC, DFLL48M, FDPLL200 が選択できます。

OSCULP32K は内蔵の32.768[kHz]の発振回路です。 XOSC32K は外部の32.768[kHz]水晶発振子を用いた発振回路です。 XOSC は外部の8~48[MHz]水晶発振子を用いた発振回路で、 XOSC0, XOSC1 の2チャネルあります。 DFLL48M は内蔵の48[MHz]発振回路です。オープンループ動作もしくは、別のクロックに対するクローズドループ動作が可能です。 FDPLL200M は内蔵の96~200[MHz]発振回路で、32[kHz]~3.2[MHz]の入力に同期したクロックを生成します。

GCLKのうち GCLK0 のクロック出力は、 MCLK (Main Clock) に使われます。 MCLKは CPU, AHB, APB にGCLK0からのクロックを供給します。

他のペリフェラルは一部を除いて任意のGCLKチャネルのクロックで動作します。

10-4-2. ペリフェラルのクロック

ペリフェラルに関連するクロックは2つあります。(図7)

1つめはペリフェラル自体の動作クロックです。 GCLK のペリフェラルに対応する PCHCTRL レジスタにより、使用するGCLKチャネルを設定します。

2つめはペリフェラルのレジスタにアクセスするためのバスのクロックです。 バスのクロック源自体は MCLK により設定されますが、各ペリフェラルにアクセスするための AHB および APB のポートに対するクロックは、一部のペリフェラルを除いてリセット直後はクロック･ゲートにより無効化されています。 よって、ペリフェラルのレジスタにアクセスするために MCLK の APBMASK や AHBMASK レジスタを設定してクロック･ゲートを開く必要があります。

11-1. ブートローダー

Wio TerminalのATSAMD51P19Aには、工場出荷時にMicrosoftのMakeCode用のフォーマットである UF2 https://github.com/microsoft/uf2を扱えるブートローダー uf2-samdx1 https://github.com/microsoft/uf2-samdx1が書き込まれています。 また、このブートローダーは、MicrochipのSAMシリーズ用標準ブートローダである SAM-BA をベースとしているため、SAM-BAのプロトコルも扱えます。いずれのプロトコルもUSB経由でファームウェアを更新できます。

ブートローダーはATSAMD51の内蔵フラッシュの先頭から 0x4000 = 16[kiB] までの領域に書き込まれています。 また、この領域はデフォルトで保護領域となっており、ブートローダーに特殊なコマンドを送らない限り、書き込みを行えません。

ATSAMD51の電源投入直後やリセット直後はブートローダーに制御が実行されます。 ブートローダーは、リセット要因が電源投入(POR)ではなく、ブートローダー起動確認RAMアドレスにマジックナンバーが書き込まれているか確認します。 マジックナンバーが書き込まれている場合は、ブートローダーのファームウェア更新処理に移行します。 マジックナンバーが書き込まれていない場合は、ブートローダー起動確認RAMアドレスにマジックナンバーを書き込んで500[ms]待ちます。 その後、アプリケーションの領域の先頭 + 4 の位置に存在するリセット･ベクタのアドレスを確認し、リセット・ベクタがアプリケーション領域内を指していれば、そのアドレスにジャンプします。

上記のマジックナンバー確認の仕組みにより、マジックナンバー書き込み後500[ms]の間にリセットされるとブートローダーの処理に移行できます。 これにより、Wio Terminalの電源スイッチを素早く2回リセット側に動かす(500[ms]以内に2回)ことにより、ブートローダーを起動できます。

11-1-1. UF2

UF2 はMass Storage Class(USBディスク)の機能を用いて、ディスク･ドライブのように振る舞い、UF2ファイルを対応するドライブにコピーすることによりファームウェアを書き込みます。

バイナリ・ファイルをUF2に変換するためのPythonスクリプト uf2conv.pyhttps://github.com/microsoft/uf2/blob/master/utils/uf2conv.py が uf2 のリポジトリにあります。 firmware.bin からWio Terminal用のUF2ファイル firmware.uf2 を作成するコマンドは以下の通りです。

python3 uf2conv.py -b 0x4000 -o firmware.uf2 -c firmware.bin

11-1-2. SAM-BA

SAM-BA はCommunication Device Class(USB-シリアル)の機能を用いて、シリアル経由でのコマンドのやりとりでファームウェアを書き込みます。 SAM-BAのプロトコルに従ってファームウェアを書き込むソフトウェアとして、 BOSSA https://github.com/shumatech/BOSSAがあります。 後述するArduino IDEからのWio Terminalへの書き込みにも、BOSSAが用いられています。 Ubuntu 20.04以降であれば比較的新しい BOSSA のコマンドを apt install bossa-cli で入れられます。 ただし、Ubuntu 18.04以前の場合、ファームウェアの書き込み時に必要なオフセットの指定機能が使えないため、自力でビルドするか、Arduinoに付属のバイナリを使う必要があります。

BOSSA のCLI版 bossac を使ってファームウェア firmware.bin を書き込むコマンドは次の通りです。

bossac -e -w -v -o 0x4000 -R firmware.bin

-e オプションで書き込み前にフラッシュを消去することを指定します。 -w オプションで書き込みを行うことを指定します。 -v オプションで書き込み後にベリファイを行うことを指定します。 -o 0x4000 オプションで 0x4000 番地 (アプリケーション領域の先頭) から書き込みを行うことを指定します。 -R オプションで書き込み完了後にリセットすることを指定します。

11-2. デバッガー

Wio TerminalのMCUのうち、ATSAMD51P19Aは比較的簡単にSWDの信号を引き出せるので、SWDに対応したデバッガを使ってデバッグが可能です。 RTL8720DNはボード上にSWDの信号が出ていないため、パッケージの端子にUEWなどで配線してSWD信号を引き出す必要があります。

SWDの信号を引き出せば、いずれのMCUもJLinkやOpenOCDを用いたデバッグが可能です。

筆者はRTL8720DNのSWDは引き出していないので、ここではATSAMD51P19A側をOpenOCDを使ってデバッグする方法を説明します。

11-2-1. OpenOCDのビルド

Ubuntuの場合aptでインストールできるOpenOCDは古く、ATSAMD51に対応していません。 よって、OpenOCDのビルドが必要となります。

OpenOCDのソースコードはSourceForge上のGitリポジトリにありますgit clone https://git.code.sf.net/p/openocd/code openocd-codeので、cloneしてビルドします。 以下は Ubuntu 20.04 LTS でOpenOCDをビルドする手順です。

sudo apt install build-essential git libtool pkg-config libusb-1.0-0-dev libhidapi-dev gdb-multiarch
git clone https://git.code.sf.net/p/openocd/code openocd-code
cd openocd-code
git submodule update --init --recursive
./bootstrap
./configure --prefix=/usr/local/openocd --enable-cmsis-dap --enable-ftdi
make
sudo make install

以上で /usr/local/openocd/bin に openocd がインストールされます。

11-2-2. OpenOCDでの接続

デバッガとしてCMSIS-DAPを用いる場合、以下のコマンドでATSAMD51P19Aに接続できます。

/usr/local/openocd/bin/openocd -f interface/cmsis-dap.cfg -c "set CHIPNAME atsamd51p19a" -f target/atsame5x.cfg

上記コマンド実行後、 gdb-multiarch でOpenOCDに接続します。

gdb-multiarch -ex "target remote localhost:3333" -ex "monitor reset halt"

11-3-1. Arduino IDE

言わずと知れたプロトタイプ作成用の開発環境です。 言語としては Arduino言語 が使えることとなっていますが、実体はC++であり、使える言語バージョンは対象のボードにより異なります。

Arduino IDEは標準ではArduinoが提供するボードのみサポートしますが、ボードマネージャーで追加することにより、サードパーティのボードを使用できます。

Wio Terminalを使うには Seeed SAMD Boards パッケージを追加します。

現時点での Seeed SAMD Boards パッケージのバージョンは 1.7.9 です。 使用できる言語のバージョンは C11+GNU拡張 (-std=gnu11) および C++14+GNU拡張 (-std=gnu++14) です。

11-3-2. MicroPython

MicroPythonは、組み込み向けに調整されたPythonの実行環境です。

PC向けのPython (CPython) のバージョン3.4、および3.5の言語機能の一部を使うことができます。 また、標準ライブラリの仕様や挙動がCPythonと異なる部分があります。

執筆時の最新バージョンは 1.13 です。

MicroPythonをターゲットボードで動かすためにはボードの定義が必要となりますが、標準でWio Terminalはサポートしていません。 一方、Wio Terminalで使われている ATSAMD51 自体はサポートしているため、ボードの定義を追加するのはそんなに難しくありません。

ただし、現時点でのMicroPythonのATSAMDのサポートは限定的なため、UARTなどの基本的な機能のみ使用可能な状態です。 よって、現時点では積極的に選択する理由はありません。

11-3-3. ArduPy

ArduPyは、Seeed Studioが開発しているMicroPythonをベースとした開発環境です。

特徴として既存のArduino LibraryのMicroPythonへのポーティングを簡単にする仕組みが用意されています。

構造としては、ターゲットボード用のArduino core (ボード定義) と、ターゲットボード用のArduPy Core (カスタム版MicroPython) を組み合わせてMicroPythonファームウェアを作るようになっています。
ユーザーは必要に応じて、既存のArduino向けライブラリのMicroPython用ラッパーを用意することにより、既存のArduino向けライブラリを比較的簡単にMicroPythonから呼び出せます。 ただし、簡単になるとはいえ、最低限、MicroPythonのモジュールを作成するための知識は必要です。

また、上記のような構造なため、ビルド用のツールとして aip というコマンドライン・ツールが用意されています。 aip 自体はPythonで記述されており、PyPIに ardupy-pip として登録されているため、簡単にインストールできます。

11-3-4. MPLAB Harmony v3

MPLAB HarmonyはATSAMD51の製造元であるMicrochip社が提供する同社のマイコン向けのソフトウェア開発フレームワークです。 MPLAB Harmony自体はGitHubの対応するリポジトリからダウンロードして無償で使用できます。

Javaで作られたGUIをポチポチすることで、ターゲット･デバイス向けの各種周辺回路のドライバやRTOSのソースコードを生成できます。 また、IARやKeilのコンパイラに加えてGCCに対応します。

周辺回路の扱いなどをある程度隠蔽してくれるため、周辺回路を用いたアプリケーションを比較的容易に作成できます。 また、RTOSの統合も可能なため、通信処理を含むアプリケーションの作成も容易です。

11-3-5. TinyGo

TinyGoはマイコン向けのコードを出力するGoコンパイラの実装です。最近Wio Terminalの対応が公式に追加されました。 現時点で筆者は触ったことがないですが、ドライバの対応も進んできているようですので、Wio Terminalで使う分にはMicroPythonよりもこっちの方がいいのではないかなと思って見ています。

11-3-6. Ameba Standard SDK

ここまでの各種開発環境はメインCPUであるATSAMD51向けのものでしたが、 Ameba Standard SDK は無線通信SoCである RTL8720DN 用の開発環境です。

通常はRTL8720DNのファームウェアとしてはSeeedが提供するものを使用しますが、開発環境が公開されているため、ユーザー自身がファームウェアを作成することも可能です。

Wio TerminalのRTL8720DN用のファームウェアとしてカスタマイズしたもののソースコードは、Seeedが管理するGitHubリポジトリhttps://github.com/Seeed-Studio/seeed-ambd-sdkで公開されています。

2020年7月2日に、Seeedの日本法人である Seeed K.K. より、Wio Terminalの無線周りのソフトウェア (ATSAMD51側のライブラリ、およびRTL8720DNのファームウェア) の修正を行うとのアナウンスがありました。 その後、7月31日に修正版がリリースされました。

12. Wio Terminalの拡張 (ハードウェア編)

12-1. Wio Terminalの外部端子

Wio Terminalにはハードウェアの機能を拡張するため、いくつかの外部端子があります。 表7に外部端子の一覧を示します。

12-1-1. Raspberry Pi 互換ピン・ソケット

本体裏面にある、2x20ピン, 2.54mmピッチのピンソケットです。Raspberry Piの拡張コネクタと同じピン配置になっています。 ただし、Wio Terminal本体と干渉するため、Raspberry Pi自体を接続することはできません。 あくまで上面にヘッダピンが出ているRaspberry Pi用HATなどを接続することを想定していると思われます。

表8にRaspberry Pi互換ピン・ソケットのピンとATSAMD51のピンの対応関係を示します。

Raspberry Pi 互換ピン・ソケットには、5V と 3.3V の電源端子があります。 これらのピンはWio Terminalの電源にダイオード経由で接続されており、ピン・ソケットからWio Terminalへの電源を供給できます。

5V はショットキバリアダイオード B5819WS 経由で接続されています。 また、 3.3V は、PNPダイオードとPチャネルMOSFETを用いた理想ダイオード経由で接続されています。 これらのダイオードにより、Wio Terminalから外部へ電流が逆流しないようになっています。

ただし、このままではWio Terminalから拡張モジュール側に電力を供給することができません。 このため、上記のダイオードと平行して、PチャネルMOSFETを用いたハイサイド・スイッチが入っています。このスイッチのON/OFFはATSAMD51のGPIOから制御することができます。 デフォルトでは 5V は OFF 、 3.3V は ON になっています。 電源と対応する出力制御用のGPIOを表9に示します。

12-1-2. Groveポート

Wio Terminalの本体下面には、左右に2つの Groveポート があります。 図11にWio Terminalの下面の写真を示します。

左側のGroveポートはI2C用で、 Raspberry Pi 互換ピン・ソケットのSDA1(3番ピン)およびSCL1(5番ピン)が接続されています。(表10)

右側のGroveポートはGPIOおよびアナログ入力用で、Raspberry Pi互換ピン・ソケットのGPIO27(13番ピン)およびGPIO22(15番ピン)が接続されています。(表11)

また、Groveポートの電源は内部の3.3Vがそのまま接続されています。 このため、外部Groveユニットへの電源の供給を行うことはできますが、GroveポートからWio Terminalへ電源を供給することはできません。

両Groveポートは、もともとの機能のほかに、ソフトウェアで設定をすることにより、ハードウェアUARTポートとして動作させることもできます。 詳細は13-1節にて説明します。

12-1-3. USB Type-Cコネクタ

Wio TerminalのUSB Type-Cコネクタは、Wio Terminalへの電源の供給、USBデバイスとして動作しファームウェアの書き込みやファームウェアからのメッセージの出力だけでなく、USBホストとして動作し他のUSBデバイスをWio Terminalに接続することにも使えます。

本書では、USBデバイスの接続については詳細は述べませんが、 接続したUSBデバイスを動作させるためには、USBデバイスを制御するためのドライバを作成して組み込む必要があります。

12-1-4. FFCコネクタ

本体右側面のスリットの奥の基板上には、20ピン、0.5mmピッチのFFCコネクタが実装されています。

現時点では公式から使い方例などは出ていません。 ATSAMD51のピン割り当てを見る感じ、ATSAMD51の余ったピンをとりあえず引きしておいて使えるようにしてあるのではないかと思います。 ATSAMD51のピン配置を表12に示します。

12-2. 拡張基板の作り方

前述の通り、Wio Terminalにはいくつかの外部拡張端子があります。 ここでは、外部拡張端子のうち Raspberry Pi互換ピン・ソケット に接続する拡張基板の作り方について説明します。

12-2-1. 拡張基板の形状とサイズ

拡張基板の形状とサイズは、Wio Terminalの筐体に干渉しない限り自由に決めることができます。 ただし、よほどの理由がない限りはWio Terminal本体のサイズと同じ形状に収まるようにした方が、Wio Terminalと拡張基板を組み合わせたときにまとまりが良くなります。

ここでは、拡張基板を収める筐体を含めてWio Terminal本体と同じ形状になる基板の形状とサイズを示します。 拡張基板の形状を決めるために必要な寸法は、SeeedのWio TerminalのページからダウンロードできるWio Terminalの基板形状のDXFファイルhttps://files.seeedstudio.com/wiki/Wio-Terminal/res/Wio-Terminal-PCB-V3.0.dxfから確認できます。

拡張基板は、幅 68[mm] 高さ 52.5[mm] 四隅の角は R3.5[mm] の面取りをした形状になります。 また、四隅からX,Yともに 3.5[mm] の位置にM2のネジを通す R2.2[mm] の穴を開けます。 Raspberry Pi互換ピン・ソケットに接続するためのピン・ヘッダは、基板上端から 11[mm] 下の位置、左右中央揃えの位置がコネクタの中心となるように配置します。

12-2-2. 基板部品面の部品配置とピンヘッダーの選定

Wio Terminal本体の下面と基板部品面の距離は、使用するピンヘッダーの形状で決まります。

例えば、廣杉計器のSMTタイプのピンヘッダー PSM-420336-20 https://hirosugi.co.jp/products/N/PSM-42.html は、実装面からピンの根元までの高さが 3.3[mm] となっています。(図13) よって、PSM-420336-20を使用すると、Wio Terminal下面と基板部品面の距離も 3.3[mm] となります。

拡張基板の筐体を用意する場合、Wio Terminal下面と基板部品面の距離から筐体の厚みを引いた長さが、部品面側で使うことのできる空間となります。 部品面側に背の高い部品を配置したい場合は、背の高いピンヘッダーを使用するなどの工夫が必要となります。

12-3. 単3・単4電池電源ユニット

12-3-1. ハードウェア

Wio Terminal本体は電源を内蔵していないため、USB Type-CコネクタもしくはRaspberry Pi互換ピン･ソケット経由で電源を供給する必要があります。

13-2. タイマー割り込みを使う

Wio Terminal用のArduino環境には、 TimerTC3/ISRBlink および TimerTCC0/ISRBlink という名前のサンプルが含まれています。 これらのサンプルはそれぞれ TC ペリフェラル、および TCC ペリフェラルのタイマー割り込みを使ってLチカをするものです。

ただし、このサンプルをコンパイルしようとすると、コンパイルエラーとなります。 これはArduino Coreに含まれるTCおよびTCCのドライバhttps://github.com/Seeed-Studio/ArduinoCore-samd/blob/1.7.9/libraries/TimerTC3/TimerTC3.cppが古いままで、ATSAMD51で動作するようになっていないためです。

よって、Wio Terminalでタイマー割り込みを使うには、現状、自前で TC もしくは TCC ペリフェラルのドライバを用意する必要があります。 サンプルとして、TC ペリフェラルのドライバを含むスケッチを用意しました。https://gist.github.com/ciniml/11b0302c1ea8fce7a360a7ed9511af91#file-isrblink-ino-L116 (リスト7)

TC ペリフェラルの初期化手順処理は以下の通りです。

  1. configureClock (115行目) 関数で、使用する TC ペリフェラルの APB クロックを有効化し、 TC の動作クロックを 1[MHz] のクロックを出力するGCLKに設定する。
  2. CTRLA レジスタの SWRST ビットに1を書き込み、SYNCBUSY レジスタの SWRST ビットがクリアされるまで待つ。これで TC ペリフェラルのソフトウェアリセットが完了する。 (38行目)
  3. TCペリフェラルを無効化するため、CTRLA レジスタの ENABLE ビットに0を書き込み、SYNCBUSY レジスタの ENABLE ビットがクリアされるまで待つ。
  4. カウンタ値を0クリアするため、COUNT レジスタに0を書き込み、SYNCBUSY レジスタの COUNT ビットがクリアされるまで待つ。
  5. 指定した周期でTCの比較一致割り込みが発生するように、プリスケーラの値と比較一致カウンタの値を決定する。
  6. WAVE レジスタの WAVEGEN ビットを TC_WAVE_WAVEGEN_MFRQ_Val (0x0) に設定し、比較一致後カウンタが0に戻るようにする。
  7. CTRLA レジスタの MODE ビットを TC_CTRLA_MODE_COUNT16_Val (0x0) に設定し、16ビットカウンタモードに設定する。
  8. INTENSET レジスタの MC0 ビットに1を書き込み、比較一致割り込みを有効にする。
  9. CTRLA レジスタの ENABLE ビットに1を書き込み、タイマーを有効にする。

サンプルでは、 setup 関数内で SAMD51TC::initialize を呼び出し、タイマーの割り込み周期を　1000000[us] = 1[s] に設定し、割り込みハンドラーとして timerIsr 関数を設定します。

タイマー割り込みが発生すると timerIsr が呼ばれます。 timerIsr 内では、組み込みのLEDの出力をトグルします。

13-3. バックライト調光

Wio Terminalの液晶モジュールは、バックライト用のLEDのアノードが3.3Vに、カソードが Q1 のNch MOSFET経由でGNDに接続されています。 また、Q1 のゲートはATSAMD51の PC05 に接続されています。 よって、PC05の出力をHighにすることでバックライトが点灯します。

単に点灯・消灯するだけであればPC05をGPIOとして制御するだけで良いです。 一方、バックライトの明るさを変えたい場合、PC05の出力をPWMなどで変調する必要があります。

では、PC05 から TCC などの内蔵のタイマー・ペリフェラルを使ってPWMを出力すれば簡単にできそうに思えます。 しかし、残念ながら PC05 には、外部割込み入力 EXTINT[5] およびSERCOMのパッド SERCOM6[1] しかつながっていません。 また、SERCOM6 はTFカードを制御するために使われている上、 SERCOMの仕様上PAD1は信号入力にしか使えません。 よって、SERCOMのSPIモードを使って擬似的にPWM信号を生成するといったこともできません。

このままでは、M5Stackでは出来ているバックライトの調光が、Wio Terminalでは実現できないということになってしまいます。 これはなんだか悔しいので、なんとか出来ないかATSAMD51のデータシートを眺めていたところ、TC, EVSYS, CCL を組み合わせればPWMを PC05 から出力できることが分かりました。

EVSYS は Event System ペリフェラルで、ATSAMD51内部のほとんどのペリフェラルからの何かしらの信号を、DMAコントローラなどの別のペリフェラルの起動トリガーなどとして分配することができます。

CCL は Configurable Custom Logic ペリフェラルで、他のペリフェラルやGPIO、EVSYS からの信号を3入力1出力LUTとD-FFで構成できる順序回路やエッジ検出回路を通した結果を EVSYS やGPIOに出力することができます。

この2つの機能を使うと、そのままでは PC05 に出力することのできない TC (Timer COunter) ペリフェラルからのPWM信号を、 PC05 から出力できます。

図18にバックライト調光時の各ペリフェラルの接続関係を表すブロック図を示します。

TC0 は 8bitカウンタ・モード で NPWM モードに設定し、入力クロック/(調光指令値の最大値*16)を周期としたPWM信号を生成します。 CCL0 はLUTの IN[0] 入力を TC0 の出力、IN[1] IN[2] 入力を0に設定します。また、LUTの真理値表を 0b10101010 に設定します。この真理値表の設定により、LUTは単に IN[0] の値をそのまま出力します。 EVSYS のチャンネル0の入力を CCL0 のLUT出力 (CCL_LUTOUT0) に接続します。 また、チャンネル0の出力を PORT のイベント入力0 (PORT_EV0) に設定します。 最後に、PORT の PC05 の出力をイベント入力0に設定します。

以上の設定により、TC0で生成したPWM信号を、CCL0、EVSYSを経由してPC05から外部の回路に出力できます。

リスト8にLCD調光を行うライブラリのソース、リスト9にライブラリを使うサンプルスケッチを示します。

また、この方法で実際にバックライトを制御する簡単なライブラリとArduinoのサンプル･スケッチをGitHubのリポジトリhttps://github.com/ciniml/WioTerminal_BackLightにおいてあります。

LCDBackLight::initialize を呼び出すと、前述の設定になるように、 TC0 CCL0 EVSYS PORT の各ペリフェラルのレジスタを設定します。

LCDBackLight::setBrightness を呼び出すと、PWMのHighの期間が指定した幅になるように TC0 のレジスタを変更します。

サンプル・スケッチでは、LCDを赤色で塗りつぶした後、50[ms] 周期で輝度値を0から100 までスイープし、バックライトの輝度値が変化することを確認しています。

13-4. ExtFlashLoader

13-4-1. 概要

Wio Terminalには 4[MiB] のQSPIフラッシュが搭載されており、ATSAMD51に接続されています。 ただし、現在のところ、公式でQSPIフラッシュにアクセスする手段は用意されていません。

そこで、QSPIフラッシュのドライバおよび、UART経由でPCからデータをダウンロードするためのライブラリとホスト側のPythonスクリプトを作成しました。

13-4-2. QSPIペリフェラル

Wio TerminalのQSPIフラッシュは、ATSAMD51の QSPI ペリフェラルから使えるピンに接続されています。 QSPI ペリフェラルは、その名のとおり、 QSPIフラッシュメモリを制御するためのペリフェラルです。

QSPIペリフェラルは、SERCOMのSPIモードと同様に、CPUから直接コマンドやデータを送受信する SPI Mode と、QSPIが割り当てられているメモリアドレスにアクセスしたときに自動的にコマンドを発行してデータを読み書きする Serial Memory Mode があります。

今回作成したドライバは、QSPIフラッシュへのデータ書き込み時はSPI Mode、データ読み出し時はSPI ModeまたはSerial Memory Modeを使います。 ドライバで使用するQSPIペリフェラルのレジスタ一覧を表15に示します。

13-4-3. QSPIペリフェラルの初期化

QSPIペリフェラルの初期化は他のペリフェラル同様、 CTRLA レジスタの SWRST ビットに 1 を書き込み、ソフトウェア・リセットを行います。

次に、 BAUD レジスタの BAUD フィールドにQSPIのクロックの分周比、 DLYBS に CS信号アサート後からはじめのクロックのエッジ出力までの遅延サイクル数を指定します。 今回のドライバでは、 BAUD = 1, DLYBS = 10 としています。

次に、 CTRLB レジスタの CSMODE フィールド に 0b01 を書き込みます。 これで、QSPIペリフェラルがCS信号を半自動的に制御し、 CTRLA レジスタの LASTXFER フィールドが 1 に設定されているときに TXDATA に書き込まれたデータの送信が完了すると、自動的に CS 信号をデアサートします。

最後に、 CTRLA レジスタの ENABLE フィールドに 1 を書き込み、 STATUS レジスタの ENABLE フィールドが 1 になるまで待ちます。

以上でQSPIペリフェラルの初期化は完了です。

13-4-4. QSPIペリフェラルの送受信

QSPIペリフェラルでの送受信は、TXDATA, RXDATA, INTFLAG レジスタを使います。

送信時は、 INTFLAG の DRE フィールドが 1 になるまで待ってから、 TXDATA にデータを書き込みます。最後のワードを送信するときは、 CTRLA レジスタの LASTXFER フィールドを 1 に、最後のワード出ない場合は 0 にします。

受信時は、 INTFLAG の RXC フィールドが 1 になるまで待ってから、 RXDATA からデータを読み出します。

送受信を同時に行う場合は、 1ワード目の送信時以外は受信処理を行い、その後送信処理を行います。 1ワード目は受信処理を行わずに送信処理を行います。

QSPIペリフェラルの初期化が完了したら、次はQSPIフラッシュの初期化を行います。

13-4-7. QSPIフラッシュへの書き込み

Wio Terminalに搭載されているQSPIフラッシュ W25Q32JVZPIM は 32[Mibit] = 4[MiB] のフラッシュ・メモリですが、内部的には 256[Bytes] のページを 16384 個集めた構造になっています。 また、ページの消去は16ページを集めたセクタ (16*256 = [4KiB])ごとにしか行えません。

よってQSPIフラッシュへの書き込みは手順は、

  1. 書き込み先のセクタがまだ消去されていなければ消去する
  2. 書き込み先のページへデータを書き込む

の繰り返しとなります。

消去や書き込みと行ったコマンドを発行する前には、必ず Write Enable (0x06) コマンドを発行して書き込みを有効にする必要があります。また、消去や書き込みコマンドの実行後には自動的に書き込みが無効化されるので、毎回書き込みを有効化しなければなりません。

セクタの消去は Sector Erase (0x20) コマンドで行います。コマンド似続けて、消去したセクタ中のアドレス (3バイト)　を送信します。

セクタの消去が完了したかどうかはステータス・レジスタの BUSY フィールドを確認します。 表17にステータス・レジスタのフィールドの内容を示します。 BUSY フィールドはビット0ですので、 Read Status Register-1 (0x05) コマンドを発行してステータス・レジスタのビット7~0を読み出します。 BUSY フィールドが 1 の間は消去処理中ですので、 0 になるまで待ちます。

ページの書き込みは Page Program (0x02) コマンドで行います。コマンドに続けて書き込み先のページのアドレス (3Bytes) を出力します。その後、ページに書き込むデータを順に出力します。 データを1ページ分出力したら、セクタ消去と同様にステータス・レジスタの BUSY フィールドが 0 になるまで待ちます。

13-4-8. Serial Memory Modeへの移行

QSPIフラッシュからの読み出しも書き込みと同様にSPI Modeでも実行できますが、後ほどSerial Memory Modeも必要となるため、Serial Memory Modeで行うこととします。

Serial Memory Modeでは、CPUのメモリ空間上にマップされたアドレスから読み出しを行った場合に、 INSTRCTRL, INSTRFRAME で設定したコマンドを自動的に発行して、対応するQSPIフラッシュ上のアドレスからデータを読み出します。

QSPIフラッシュからの読み出しには、 Fast Read Quad I/O コマンドを使用します。 図19にFast Read Quad I/Oのフレーム構造を示します。

上記のフレームを自動的に送信できるように、INSTRFRAME, INSTRCTRL レジスタの各フィールドを設定します。 表18にINSTRFRAMEレジスタ、表19にINSTRCTRLレジスタのフィールド一覧を示します。

実際にSerial Memory Modeで動作するように変更する手順は次のとおりです。(リスト10)

まずはSPI Modeの状態でステータス・レジスタの QE (bit9) フィールドに1を書き込みます。 Read Status Register-2 コマンドを発行して ステータス・レジスタの15~8ビットを読み出した後、9ビット目を1にした上で Write Status Register-2 コマンドでステータス・レジスタの値を更新します。

次に、動作モードの変更のため、QSPIペリフェラルを一旦無効化します。 CTRLA レジスタの ENABLE に 0 を書き込んで、STATUS の ENABLE フィールドが0になるまで待って、QSPIペリフェラルを無効化します。

次に、 CTRLB の MODE フィールドを 1 に設定してSerial Memory Modeで動作するようにします。 その後、INSTRFRAME、INSTRCTRLの各レジスタの値を前述の通り設定します。

最後に CTRLA の ENABLE フィールドに 1 を書き込んで、STATUS の ENABLE フィールドが 1 になるまで待ってQSPIを有効にします。

ここまででQSPIをSerial Memory Modeに移行できましたが、最後にCPUのキャッシュラインをすべて無効化 (invalidate) しておきます。

CMCC の MAINTO レジスタに 1 を書き込むと、現在のキャッシュラインを (invalidate) します。 その後、一応メモリ・バリア(__ISB(), __DSB())で全メモリへのアクセスが完了するまで待機します。

13-4-9. QSPIフラッシュからの読み出し

Serial Memory Modeに移行した後は、CPUからみて 0x04000000 から始まるアドレスへ読み出しアクセスをすることで、QSPIフラッシュからデータを読み出すことができます。

例えばQSPIフラッシュのアドレス 1234 のデータを読み出す場合は、

auto qspi_ptr = reinterpret_cast<const std::uint8_t*>(0x04000000);
auto data = qspi_ptr[1234];

などとします。

13-4-10. ライブラリ ExtFlashLoader

前述までのて操作を行うArduino用ライブラリとして、 ExtFlashLoader を作成しました。 また、リスト11に、プログラム内に格納されたバイナリ・データをQSPIフラッシュに書き込むサンプル・スケッチを示します。

ExtFlashLoader::QSPIFlash クラスが、QSPIフラッシュのドライバの本体です。 スケッチのグローバル変数としてインスタンス qspiFlash を定義しておきます。

setup 関数内で、qspiFlash.initialize() と qspiFlash.reset() を順に呼び出します。 その後、QSPIFlashを使ってQSPIフラッシュにバイナリデータを書き込む ExtFlashLoader::writeExternalFlash 関数を呼び出します。 以下に writeExternalFlash の宣言を示します。

static bool writeExternalFlash(QSPIFlash& qspi, std::uintptr_t address, const void* data, std::size_t length, WriteExternalCallback&& callback );

第1引数に QSPIFlash のインスタンス、第2引数に書き込み先のQSPIフラッシュ上のアドレス、第3引数に書き込むデータの先頭へのポインタ、第4引数に書き込みデータのサイズ(バイト単位)、第5引数に書き込み処理の進捗状況を受け取るコールバック関数を指定します。

このように簡単にQSPIフラッシュへデータを書き込むことができます。

13-5. SimpleLoader

ExtFlashLoader を使うことにより、QSPIフラッシュへアクセスできるようになりました。 一方、ATSAMD51にはQSPIフラッシュから命令を読み出して直接実行する機能があります。 よって、QSPIフラッシュに書き込んだプログラムをそのまま実行することができます。 また、このときATSAMD51の内蔵フラッシュ・メモリにはアクセスしていないので、 内蔵フラッシュ・メモリを書き換えることができます。

この機能を用いて、TFカード内に保存されているアプリケーションの一覧を表示し、ユーザが選択したアプリケーションを内蔵フラッシュ・メモリに書き込むアプリケーション SimpleLoader を作成しました。https://github.com/ciniml/WioTerminalSimpleLoader SimpleLoader はQSPIフラッシュ上で動作します。

現在のWio Terminal用のArduino coreでは、プログラムをQSPIフラッシュ上のアドレスに配置することができないため、 Simple Loader は MPLAB Harmony v3で作成しています。

SimpleLoaderを書き込むためのサンプル・スケッチは WriteSampleMenu サンプルとして ExtFlashLoader に含まれています。

SimpleLoader は、TFカードの /apps ディレクトリにあるアプリケーションを一覧表示するようになっています。 各アプリケーションは個別のディレクトリに分けて格納します。

/apps
 +- app1
    +- app.bin --- app1のバイナリ
    +- app.png --- app1の内容を表す画像 (オプション)
    +- name    --- app1の名前を含むテキストファイル
    +- desc    --- app1の説明文を含むテキストファイル (オプション)
 +- app2
    +- app.bin --- app2のバイナリ
    +- app.png --- app2の内容を表す画像 (オプション)

アプリケーションのバイナリを app.binとして格納します。

name はアプリケーションの名前を含むテキストファイルです。最大64バイトまでです。

desc はアプリケーションの説明文を含むテキストファイルです。最大64バイトまでです。

app.png はアプリケーションの内容を表す画像ファイルです。表示領域は160x120ですので、それ以下の画像を格納します。

14. おわりに

Wio Terminal発売後から4ヶ月ほど触ってみましたが、現在でも未だ開発環境周りは発展途上です。

ハードウェアとしては、安価で強力な無線機能が日本国内で合法的に使える上、ESP32のようなLLVMが公式でサポートしていないMCUではなくARMコアのMCUを使っているため、 様々な開発環境が移植できる可能性があります。

また、Raspberry Pi互換ヘッダーはピン数が多く、さまざまな拡張基板を作れる可能性があります。 現時点ではまだ3種類しかつくっておらず、筆者以外に拡張基板を作っているユーザーは見かけませんが、これからいろいろモジュールが出てくることを期待しています。
